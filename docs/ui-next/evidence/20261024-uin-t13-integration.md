## Attended date-field defect and repair

During the bounded 125% package walkthrough, the Owner reported that date text was invisible and the input box/calendar button were oversized at both 100% and 125%. A local PrintWindow diagnostic of the package reproduced the blank, clipped Goods date field; it is not published. Native UIA measured the date composite around 188 physical pixels tall inside a metadata field around 75 physical pixels tall at 125%. The walkthrough fixture completed and drained its owned SQL resources, but that PASS only establishes fixture lifecycle. The Owner did not give a dated A14 acceptance decision.

The root cause was in the shared `BootstrapDateInput` constructor: after docking its native text and calendar children, it read their stretched heights and adopted the default `UserControl` height of 150 px at 100% (about 188 physical px at 125%). The upstream RED test measured 150 px against a themed 32–34 px contract; the app RED test failed 4/4 Light/Dark compact layouts, measuring a 150 px date input in a 60 px field. The UI fix captures the children's preferred height before docking. The focused UI DateInput/CalendarPicker selection passed 67/67 on each of `net48` x86 and `net8.0-windows`; the complete UI solution built both targets with zero warnings/errors. At native125, the consuming app's compact Goods layout passed 4/4 and Sales filter/required date keyboard and layout passed 4/4. The repaired-package attended review then took place at native100.

The repaired package v3 opened a bounded attended fixture at native100 after the final automated runs. A local PrintWindow diagnostic showed the Goods New date `24/10/2026` readable, with the input and calendar button fitting their metadata row; this diagnostic image stays under ignored `.local/t13` and is not published. The Owner reported directly reviewing Goods/Sales dates and invalid-date feedback, Light/Dark contrast, canceled tab close retaining Note, and Refresh/busy, with no remaining UI error, and explicitly **accepted UIN-T13 on 2026-10-24**. This is an attended native100 decision; native125 on v3 has automated layout/package evidence but no separate Owner visual re-review.

The attended fixture's `TestResults/t13-attended-v3-100/t13-attended-v3-100.trx` is **1/1 FAIL** at `AssertNoInventoryAsync`: its first query found one `GoodsReceipts` row in the owned temporary database. The Owner subsequently confirmed pressing Save during the walkthrough. The available assertion did not record that row's status or any ledger totals, so no Post or stock change is inferred. The same probe reported `UIN_T13_ATTENDED_READY=PASS`, `UIN_T13_ATTENDED_DRAINED=PASS`, and `APPLICATION_DRAINED=PASS`. Its resource record states `DatabaseAndAllPrincipalsDroppedAfterVerifiedDrain`; an independent read-only check against designated non-production `master` found zero remaining database and zero remaining matching principals. The failed fixture's ignored `ready`/`complete` marker files remain locally: automatic approval review rejected their removal as `blocked by policy`. The FAIL is retained and never counted as a PASS.

To distinguish that deliberate Save from an implicit application write, the same package fixture was rerun at native100 without human interaction. Its `TestResults/t13-attended-v3-100-idle/t13-attended-v3-100-idle.trx` is **1/1 PASS**, including the zero-document assertion. The final resource record reports `DatabaseAndAllPrincipalsDroppedAfterVerifiedDrain`; the fixture removed its own `ready`/`complete` barrier and no Desktop app process remained. This control does not replace the Owner's attended UI observations or change the failed result above.
