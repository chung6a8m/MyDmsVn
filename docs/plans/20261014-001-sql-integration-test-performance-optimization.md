**Status:** SQLPERF-T01 implementation complete / live acceptance blocked (2026-10-14). The mutation guard, durable ownership journal, opt-in timing, audited migration manifest, independent inventory/TRX parser, Job Object watchdog, runner and sanitized report primitives are implemented and pass non-SQL automated gates. The operator approval file is absent in this environment, so no live SQL DDL, warm baseline, instrumentation-overhead measurement or unfiltered dual-TFM SQL acceptance was run; Gate T01 remains open. **Type:** cross-phase test-infrastructure hardening, not a new business feature or a change to completed P3.1. **Base:** `main` after merged PR #18 (code baseline `130ab55787a2718cb590754662715393e094dade`; merge commit `810136c7aca65c2970194d8a6de87cf68353d53f`). **Target:** Windows, SQL Server 2017+, `net48` and `net8.0`. May proceed independently of P4.1, but must not delay or weaken P4.1/P5/P6 correctness gates.

Read before implementation: `AGENTS.md`, `docs/DEVELOPMENT_PLAN.md`, `docs/TEST_STRATEGY.md`, `docs/P3_1_VERIFICATION.md`, `docs/PERSISTENCE.md`, `docs/SCHEMA_COMPATIBILITY_AND_MIGRATION_RUNBOOK.md`, this plan and relevant test source. These are requirements for subsequent implementation, **not** evidence that any task has already passed.

These are planned implementation requirements, not completed evidence.

**Round-2 review closure (2026-10-14):** This specification additionally requires an in-harness SQL mutation guard, durable crash-recoverable test DB ownership and complete reconciliation of migration timing invocation paths. Requirements are not evidence of implementation.

**T01 implementation evidence (2026-10-14):** See `docs/SQLPERF_T01_VERIFICATION.md`. Source/discovery lists 210 cases for each TFM and the audited migration manifest contains 41 call sites. These discovery and synthetic results do not substitute for the blocked approved-instance baseline; no T01 checkbox or Gate is considered complete until the live criteria pass.

## 1. Objective and scope

Reduce end-to-end duration of the SQL integration suite **without** reducing security, schema/migration, identity, inventory, race-condition, cleanup or two-TFM coverage. Diagnose first, then optimize one mechanism at a time with measured A/B evidence. Keep all production schema and SQL authorization semantics unchanged.

**Initial target (engineering goal, not an automatic release gate):** reduce median warm-run wall-clock by **20–30%** on *each* framework relative to same-machine, same-SQL-instance baseline, with no loss of assertions or increase in failures. If this is unattainable without sacrificing isolation, keep safety and document the measured tradeoff. Count execution time including fixture setup/teardown; optimizing only `dotnet test` launcher overhead has limited value.

- `GoodsReceiptCommandIntegrationTests.Deactivation_and_post_serialize_in_both_lock_orders_for_every_reference` took about **34s** in each TFM. The test exercises three reference types × two lock orders, and its test-only SQL triggers include `WAITFOR DELAY '00:00:05'`. SQL `WAITFOR` delta was about **55.2s** per TFM. This wait is intentional synchronization overhead; it is not itself evidence of slow SQL execution.
- SQL instance wait deltas included `LCK_M_*` about 68.4s/59.2s and `RESOURCE_SEMAPHORE_QUERY_COMPILE` about 40.5s/45.4s (net8/net48). Wait deltas can overlap and may include activity external to tests: **never add them directly to test wall-clock** or treat them as definitive root cause.
- SQL process sampled working set roughly **320 MB median**, **337 MB maximum**, with configured `max server memory = 1536 MB`. These samples do **not** establish that SQL has no memory pressure; in particular, working set is not the same as SQL memory committed/target. Do not change SQL memory settings solely from this observation.
- There was **no overlapping test execution** in TRX; the observed SQL test database count maximum was one. `dotnet test` wrapper overhead was small (roughly 1.6–3.9s).
- The single-run operator diagnostics above are **historical observations only**, not the statistical A/B baseline. Before behavior-changing optimization, perform one labeled warm-up and **at least three valid warm measured runs per TFM** against an unmodified baseline. Compare candidates using at least three equivalent valid warm runs per TFM; if baseline code/inventory/environment changed, establish a new matched baseline rather than extrapolating from the original snapshot.

## 2. Source-derived bottlenecks and safety constraints

1. `tests/MyDmsVn.Server.Infrastructure.IntegrationTests/AssemblyInfo.cs` currently specifies `[assembly: CollectionBehavior(DisableTestParallelization = true)]`. This was introduced to avoid local SQL overload and command timeouts when many disposable databases/migrations run in parallel. **Do not remove it as a first optimization.**
2. `SqlTestDatabase.CreateAsync` issues `CREATE DATABASE` for each isolated test setup. `SqlTestDatabase.DisposeAsync` uses `SqlConnection.ClearAllPools()`, `ALTER DATABASE ... SET SINGLE_USER WITH ROLLBACK IMMEDIATE`, then `DROP DATABASE`. Repeated DDL, migration and global pool eviction plausibly cost time, but their per-stage durations are not yet measured.
3. `DatabaseMigrationRunner.Migrate` runs DbUp with session-scoped application lock, preflight and `WithTransactionPerScript()`; SQL schema manifests, rollback and lock correctness are part of production safety. Do not bypass DbUp, remove SQL locks/preflight, or mutate numbered migration scripts to make tests faster.
4. Some tests intentionally verify real multi-session locking, connection pooling, interrupted migration, schema drift, permission approval, audit and cleanup. They **must not** share dirty databases or be rewritten as mocks in place of existing real SQL acceptance checks.
5. SQL tests must continue to accept only an explicit `MYDMSVN_TEST_SQLSERVER_CONNECTION_STRING` targeting `master`, create guarded disposable `MyDmsVn_Test_<GUID>` databases, and never delete an unowned database. Preserve failure cleanup, retryability and cancellation boundaries.
6. Leave `net48` and `net8.0` supported; SQL Server 2017 syntax and Windows/.NET Framework requirements remain in scope. Do not change the production database or release application behavior solely for test speed.

Record `created`, `drop-intent`, `disposed`/`cleanup-failed` transitions; add a per-database ownership marker after creation where feasible. Ensure safe multi-process locking, interrupted/partial write detection, replay/restart idempotence, and no sensitive host/connection string data in shareable evidence. A journal record or `MyDmsVn_Test_<GUID>` name **alone cannot prove ownership**. For automatic cleanup, corroborate exact approved instance, intended DB identity, live creation metadata and ownership marker where present; explicitly account for the crash window after SQL CREATE but before durable `created`/marker registration. If independent corroboration is insufficient, quarantine the DB for operator review **without DROP/KILL**, report incomplete rather than green, and never clean another active run's database.
- [ ] Establish in T01 a **reviewed independent SQL-test inventory** from all discovered xUnit `[Fact]`/`[Theory]` methods and expanded cases in the integration assembly, **not** from `SqlServerFact`, future `FastSQL`/other traits or the runner's SQL-filter selection. ### SQLPERF-T02 — Replace fixed 5s waits in SQL concurrency probes (PR 2)

- [ ] Inventory every test-only SQL `WAITFOR DELAY '00:00:05'` use (currently in `GoodsReceiptCommandIntegrationTests.cs` trigger helpers), map each to the lock owner, blocked session, signal and assertion. Preserve six lock-order scenarios across `Warehouses`, `Employees` and `Products`, plus same-receipt, StockBalances and catalog races.
- [ ] **Pilot one isolated scenario first:** prefer a **separate SQL application-lock release gate** (`sp_getapplock`) with a unique, per-test/scenario resource name in the owned disposable DB. A dedicated controller connection acquires an exclusive **session-owned** gate *before* the first business operation. The test-only trigger requests an incompatible **transaction-owned** application lock *inside the business DML transaction while its intended business locks remain held*. Use a distinct observer SQL connection for DMVs; neither the observer nor controller may request business-row locks while the gate is held. Prove no dependency cycle, including through trigger side effects, before reuse. Identify holder and contender by verified SPID/database, check that the holder is waiting on the **APP gate** while retaining the expected business locks, then that the contender is blocked on the **expected business resource** (not the gate), and only then release the controller lock. Use bounded gate lock timeouts, SQL command timeouts, .NET cancellation and `finally` cleanup. Never replace 5s waits with shorter arbitrary `WAITFOR`/`Task.Delay`.
- [ ] Define a **non-blocking observable gate-arrival signal**: the existing `dbo.TestConcurrencySignals` insert occurs inside an **uncommitted trigger transaction**, so querying it with normal `READ COMMITTED` may block until the gate is released and must **not** be the progress condition. Prefer DMV observation of the identified holder session's APP-lock request in `sys.dm_exec_requests`/`sys.dm_tran_locks` with expected database, wait status and controller blocker; treat optional `WITH (NOLOCK)` polling of a uniquely keyed, uncommitted signal row as **provisional diagnostic only**, never sole evidence. Observation must not wait on application/business row locks, share the holder transaction/connection or claim an unrelated APP wait proves trigger entry. Fail closed if permissions/metadata cannot distinguish the gate wait and held business locks. Test that observer returns promptly while the trigger transaction remains uncommitted (including with default `READ COMMITTED` on other connections).
- [ ] Define/document a deterministic sequence: **acquire controller gate → start holder → prove holder reached APP gate without blocking observer and still holds intended business locks → start contender → observe actual `LCK_M_*` wait on the expected business table/key/resource → release controller gate → await both operations → assert and cleanup**. Verify wait-resource attribution on the SQL Server versions in scope; distinguish APP waits from business KEY/PAGE/OBJECT/HOBT waits, not merely `LCK_M_*`. Cover different catalog/stock lock orders; do not impose a generic gate on a scenario whose original business lock order cannot be preserved.
- [ ] Where the current trigger is required to pause execution *inside a business command*, use test-only trigger/database artifacts in its **owned disposable database** (or a test-controlled seam), without altering production authorization, migration scripts, schema artifacts or UoW behavior. A test must never need a privileged/broad SQL permission solely to fake the state. If a scenario genuinely cannot be made deterministic without intrusive production hooks, retain its existing fixed delay and document the reason; do not weaken the assertion.
- [ ] Prove both lock orders, race winner/loser, idempotent posting, rollback, no orphaned trigger/table/session and post-test database disposal. On any assertion failure or timeout, **release controller gate in `finally`**, cancel SQL commands where possible, bound-wait/observe each started Task to completion (or terminate **only** owned disposable connections/sessions), and **only then** tear down the test database. An existing `Task.WhenAny` timeout without cancellation does not stop the SQL task. Use SQL lock/command timeouts consistent with the runner watchdog, and test failure injection before/after gate acquisition, during DMV observation and before release. Never leave unobserved background operations accessing a DB after `DisposeAsync()`.
- [ ] Re-run each modified concurrency test at least **20 consecutive times per TFM** under development SQL conditions (or document environment limitation), then complete both SQL suites. On every relevant iteration, verify non-blocking holder gate-arrival observation, required pre-release business locks and contender business-resource blocking; inject failure before/after acquiring gate, during DMV/signal observation, when holder has entered the trigger and before controller release. Ensure bounded task cancellation/drain, trigger/session cleanup and useful redacted diagnostics on failure.

**Gate T02:** No assertion deletion or skipped cases; the control-gate observer demonstrably **does not block on an uncommitted trigger signal**, the holder's APP-gate wait and the contender's **actual expected SQL business blocking** are independently observed before release, and the barrier demonstrably cannot deadlock on its own control signal. SQL task completion and cleanup are bounded even on failure, and affected test duration measurably decreases. A faster but non-deterministic race test is a failure; if the pilot fails, retain the original implementation and document findings.

## 5. Required safeguards, exclusions and reporting

- **No weaker tests:** preserve independent multi-session SQL tests, their actual blocking proof, permission deny/approval cases, migration fingerprints, history/drift, transaction rollback, identity/bootstrap and bounded cleanup. No `Skip`, hidden `--filter` or narrower assertions to achieve a performance number. Enforce preflight + zero skipped mandatory SQL cases even when `dotnet test` returns success.
- **No dangerous shortcuts:** never bypass `SqlTestDatabaseName.EnsureDisposable`, use SQL instance identity inferred solely from a connection string as proof of safety, connect to an unapproved/production SQL instance for DDL, rewrite migrations 001–008, grant broad runtime SQL rights, disable the schema checker, or add a production-only test hook without architectural review. Require independently reviewed non-production instance approval before any SQL create/drop probe. Do not treat generated DB names or the ownership journal as sufficient deletion authorization, bypass the mutation guard with direct execution, auto-drop ambiguous crash-window DBs, or claim migration timing coverage while direct DbUp paths are uninstrumented.
- **No unsafe parallelism:** retain the current assembly serial default until adversarial isolation/capacity evidence supports changing it; keep a simple revert switch.
- **No diagnostic secret leaks:** performance logs/TRX may contain exception messages. Sanitize connection strings, credentials, local paths, PII and any password/hash; raw evidence stays local, shareable ZIP is reviewed before publication.
- **No fabricated results:** report unsupported Windows/SQL/DMV environments as blocked/not run. Distinguish profiling hypotheses from verified savings.

For each PR/task, deliver a small before/after comparison table, changed files, exact test commands, passed/failed/skipped counts, timeout/cleanup behavior, SQL resource measurements if available, and a go/no-go decision for the next optimization. PR 1 should provide measurement before PR 2–4 alter test behavior.
