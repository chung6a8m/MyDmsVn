## 0. Mission, constraints, ownership

Roadmaps WEB1–WEB3 are archived. WEB3 proved bounded Receipt → Inventory → Sales against non-production SQL through net48/IIS Express/HTTPS. WEB4 creates repeatable backend CI and a durable, queryable, transactionally correct idempotency boundary for the SIX existing Web mutation operations (Sales and Goods Receipt: Create, Update Draft, Post), then verifies failure/reload/recovery jointly with the Web client.

**Preserve:** net48, existing System.Web/Web API 2/Katana host, bearer JWT + authoritative SQL session + HttpOnly Secure Strict refresh cookie, same-origin HTTPS/CSP/CSRF/Origin, MediatR/Application authorization, explicit UoW and SQL transaction ownership, linq2db, DbUp, schema10 desktop admission, schema11 Web history, decimal/int64 string wire, receipt unique-product vs Sales duplicate/gift rules, moving-average stock ledger and frozen COGS. The independently selected CEX-A01–A05 WinForms workstream stays ACTIVE and untouched.

**Not selected:** full IIS/production acceptance, distributed rate-limiter redesign, complete operator audit retention deployment, Web payments/returns/transfers/stock adjustment, changes to Local transport or business costing, automatic failed-write retry, switching from net48, blanket dependency upgrades, new SQL test framework, hosted public SQL with secrets. The WEB2 full-IIS exception is not a WEB4 PASS.

Authoritative ownership: this plan owns B01–B06; frontend companion owns F01–F05. [Backend operation contract](../design/WEB4_IDEMPOTENCY_JOURNAL_CONTRACT.md) owns journal/wire/transaction rules, [ADR 0014](../adr/0014-web4-durable-operations.md) records the proposed design direction, [backend acceptance matrix](../development/WEB4_BACKEND_ACCEPTANCE.md) owns SQL/HTTP cases and [Codex handoff](../development/WEB4_CODEX_HANDOFF.md) owns execution order. ## 4. B03 — Web-only schema 12 and transaction-owned journal (VERIFIED CANDIDATE; Owner pending)

**Prerequisite:** B01 canonical schema/atomicity design merged. Tentative migration name 012_WebOperationJournal.sql; final path/name must match inspected DbMigrator and schema-source conventions. **Source-specific patch required:** DatabaseMigrationRunner.ValidateWebSchemaStateBeforeMigration currently permits exact10→Web on TooOld but not an exact11→12 upgrade; introduce a frozen exact11 gate, not a loose script count check. Do NOT edit scripts 001–011 or desktop CurrentScripts. Web checker must admit exact new Web script+fingerprint and reject schema10/11 when WEB4-enabled host expects 12, too-new and partial/unmanaged variants. DbMigrator opt-in --web must have safe 11→12 admission; no automatic Desktop migration; preserve exact10 desktop behavior and refuse mixed desktop/schema12 writer claims.

Suggested physical fields, refined by B01: OperationId uniqueidentifier (GUIDv4), ActorUserId int, OperationKind/RouteScope, RequestHash binary(32), ResourceDocumentId bigint NULL, OutcomeCode and **command-specific versioned replay result** (full original authoritative Write detail for Create/Update; Sales Post with version; Receipt Post without version), CreatedAtUtc/CompletedAtUtc; PK/unique actor+operation key, explicit checks/indexes and a retained non-reusable key tombstone after payload retention ends. Add a stable Web deployment/database epoch from a read-only runtime surface, with privileged rotation on logical replacement/rewind. Choose stored payload type/size only after measuring actual authoritative Create/Update detail and required precision. No session token, password, refresh cookie, access JWT, full request raw body or uncontrolled error text. Enforce least privilege for a separate Web runtime journal access path; no DELETE to runtime, no db_owner, no desktop grant widening.

Journal claim/read/finish MUST use uow.Repository<...> bound to ISqlExecutionContext.Connection AND Transaction. Use transaction-owned lock/key serialization and unique constraint, no application-static semaphore; honor lock ordering before stock-gate/receipt header locks. A journal row indicating committed completion MUST be committed atomically with business changes, including line/ledger/balance/value and stored replay result. A rollback leaves no committed success. SQL errors or commit acknowledgement loss yield UNKNOWN on client, not a second Post. Never leave a committed processing row unless B01 separately specifies safe terminal recovery semantics.

**Tests:** fresh Web12, exact11→12, supported exact10→Web12 and prohibited schema9→12; fake/partial/spoofed Web11, too-new, fixed historic script/fingerprint and both under/overgrant; DB epoch rotated after clone/rewind and stable after restart; transaction rollback/fault injection; same-key competing writes; same-key different fingerprint; immutable key tombstone after response expiry; schema10 desktop baseline unaffected. **New mandatory Local SQL gate:** invoke Sales Create/Update/Post and Goods Receipt Create/Update/Post via Local/Application on exact schema10 with WebOperationMetadata absent; assert no journal access/requirement, same rowversion/permissions, ledger/valuation/COGS, rollback and no duplicated effects. Source owner examples: Inventory.Tests SalesReceiptDraftTests, SalesReceiptPostTests and GoodsReceiptCommandIntegrationTests; validate discovered methods before invocation. No broad upgrades.
**Epoch gate:** Web runtime may only SELECT the epoch from its own SQL database; one request's epoch check and its business transaction/status lookup must operate on that same authoritative database. Verify stale epoch after logical DB replacement/restore fails **before** a write or status reveal, even with same userId, and also with a stale in-flight browser tab. Never depend solely on client-side IndexedDB partitioning.

## 5. B04 — Six idempotent Web mutation APIs and readback (PLANNED)

**Prerequisite:** B03 journal and B01 pinned protocol. Keep Sales/Receipt controller routes, successful JSON envelope/status/precision and existing Application validation. Extend via shared narrow Web idempotency coordinator/command metadata, not copy/paste business handling. Enforce key format and canonical fingerprint after strict wire decode; reject malformed/missing keys in WEB4-enabled mode. Legacy Web11/old client compatibility requires explicit coordinated deployment mode, not silent fallback.

Six requests: POST Sales Create; PUT Sales Draft; POST Sales Post; POST Goods Receipt Create; PUT Receipt Draft; POST Receipt Post. **Return/replay contracts vary:** Create/Update recover original full authorized detail, including real version and line IDs/order, with Write permission even without Read; Sales Post returns original version; Receipt Post intentionally has no version. No post-commit Get may reconstruct those results. Re-authorize CURRENT required operation grants before exposing an existing journal result, but do not re-run dynamic business validators or re-Post an already committed operation. A key belongs to exactly one actor and one immutable request fingerprint; same actor/key+same payload returns the completed outcome without another side effect (after fresh authorization); reused key with different route/body/version returns deterministic Idempotency.KeyConflict. Concurrent duplicate requests must serialize safely across workers; no duplicate source, ledger or stock valuation. Re-check CURRENT authoritative session, account, revoked permissions and operation-owner before replay/status. Authorization must be enforced before exposing stored results; never interpret JWT grants or UI capability as authority. Read permission is not implicitly required to recover the **original complete Write/Post-authorized command result**; status MUST return no MORE than those original permitted fields and MUST NOT issue Get/Read, but may return the full original Create/Update Write detail with version/line identities.

Proposed protected query: GET /api/v1/operations/{operationId}, keyed by current authenticated actor, **server-verifying X-MyDmsVn-Deployment-Epoch and X-MyDmsVn-Operation-Fingerprint** against the current SQL database + immutable journal entry; distinguish committed result and not-observed/unknown, with no implication that 404 means safe to retry. Returned protected identity metadata (operationId, kind, method, routeScope, original requestTargetId—null for Create, SHA-256 fingerprint, epoch; the resulting created document ID is distinct) must match the client's recomputed frozen intent before SETTLED. Strict no-cache/no-store, no query secrets or cross-actor existence leak. Response and error schema stay within canonical wire/error design. On known successful Post, status is terminal Posted with the **original Sales version when Sales**, and no fabricated version for Receipt; unknown stays locked until positive evidence or the controlled original-intent resolution path. Readback 404/timeout is not proof of rollback. **Explicit same-key resend after user confirmation** may be enabled only after B03/B04 concurrent in-flight, crash/restart and key-tombstone tests prove at-most-one business effect. Never silently generate a new operation key for an unresolved intent. Server must not auto retry deadlock victim, timeout, loss of response, conflict or failed writes. Revalidate existing Sales/Receipt guest/denied/outcome-unknown/409/Get403 regression.

**Exit:** reviewed HTTP unit+authorization tests and real SQL same-key/resend/conflict tests, no drift in existing WEB2/WEB3 wire fixtures, no business cost rewrite. Backend HTTP success or replay must not claim browser acceptance.
