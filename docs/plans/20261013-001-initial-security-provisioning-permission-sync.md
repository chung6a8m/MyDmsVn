# P3.1 — Initial security provisioning and continuous permission synchronization

Status: **Not started** (2026-10-13). Follow-up to completed P3, **not** retroactive completion evidence for P3. Depends on P1–P3 identity, password, schema and authorization foundations. Must be verified **before P4.1 authenticated desktop login walkthroughs, P5 interactive acceptance or P6 release**.

Read: `AGENTS.md`, `docs/SECURITY.md`, `docs/DEVELOPMENT_PLAN.md`, `docs/CONFIGURATION_AND_SQL_SECURITY.md`, `docs/P3_VERIFICATION.md`, `docs/TEST_STRATEGY.md`, `docs/plans/20261008-007-phase-6-local-hardening.md`.

## Objective

On a fresh application database, provide a **controlled, auditable, one-time first-administrator enrollment** and a **repeatable per-release permission synchronization mechanism**. Every new feature/module declares its permission keys in source code; deployment synchronizes the authoritative catalog and eligible Administrator grants without hardcoded passwords, permission bypasses or manual per-module seed scripts.

P3 created `Users`, `Roles`, `UserRoles`, `RolePermissions` and `UserPermissions` and the Login/BCrypt infrastructure; the existing `002_Identity.sql` does **not** provision an application Administrator. A SQL/DBA migration principal is **not** the same as an application user assigned the Administrator role.

## Non-negotiable security and architecture rules

- Keep existing authentication/authorization: authenticated active user, direct `UserPermissions` decision first (explicit deny still wins), otherwise active role union, unknown permission **deny**. The additional **runtime catalog activation gate** must be satisfied **before** considering any direct or role assignment: a key must be both declared by the running Application build and present in the SQL registry in an explicitly activated state. An unknown, unregistered legacy, pending-activation or deprecated key always denies, even if a matching historical assignment exists. Do not confuse catalog activation with Administrator auto-grant approval; they are independent decisions. No `IsAdministrator` / role-name shortcut, blanket bypass, wildcard permission or automatic direct-user grants.
- SQL **runtime principal remains least-privileged** and unable to INSERT `Users` or INSERT/UPDATE `Roles`, `UserRoles`, `RolePermissions`, the new registry, managed-grant policy or bootstrap state. Preserve only the **existing explicitly allowlisted password/algorithm/audit-column UPDATE on `Users`** required by the P3 login/rehash path; never grant runtime user creation, role/permission management or bootstrap writes. Use a separate **operator-invoked privileged provisioning/sync command** (or an explicitly scoped maintenance principal), never desktop startup, Login, LocalApiClient, HTTP request or ordinary installer.
- DbUp numbered migrations remain **immutable**; introduce a new additive migration after `007_Inventory_Stock.sql` if needed. Do not rewrite `002_Identity.sql`, journal history or existing user data.
- No default administrator username/password, shipped BCrypt hash, secret in source, config, command-line arguments, environment-variable dumps, CI output, screenshots or logs. Do not expose SQL admin credentials to the desktop.
- Do not seed production catalog/business data here. All SQL tests use guarded disposable databases; no unattended production reset.

## Task list and dependency order

### P3.1-T01 — Permission catalog architecture and stable declarations

- [ ] Define an explicit version-controlled `PermissionDefinition`/`IPermissionRegistry` model (at minimum exact `Key`, owning module, description, lifecycle status and administrator auto-grant eligibility/sensitivity). Existing P5 `Catalog.*`, `Inventory.*` and `Security.*` keys must be registered without renaming public keys.
- [ ] Each module declares its own constants/definitions and registers them via an explicit deterministic composition entry point in the shared Application/Domain-appropriate layer; **no UI/SQL-dependent scan, reflection-order reliance or hidden duplicate definitions**. Adding a feature includes its declaration, registration, authorization checks, tests and deployment manifest changes in the same PR.
- [ ] Validate duplicate keys, invalid/blank keys, casing/ordinal equality, collisions between modules, excessive length (current SQL key limit: 100 characters), descriptions and lifecycle metadata. Fail release validation on omissions; a permission referenced by a handler but absent from the registry must not silently work via a preexisting SQL grant.
- [ ] Specify two separate policies in `PermissionDefinition`/the release manifest: **catalog activation** (`PendingActivation`/`Active`/`Deprecated`, with unregistered historical keys tracked separately) and **Administrator managed-grant eligibility/approval**. A permission may be active for explicitly authorized non-Administrator principals while its Administrator grant remains pending; enabling a key may not silently activate preexisting unreviewed grants.
- [ ] Build a deployable **versioned registry snapshot/manifest** from the deployed application modules, not a mutable ad-hoc list typed by an operator. Support old/new client compatibility review when the shared DB is upgraded.

### P3.1-T02 — Additive SQL registry migration and compatibility

- [ ] Propose/document a `dbo.Permissions` catalog (exact `PermissionKey` unique with binary/ordinal semantics consistent with existing `RolePermissions`/`UserPermissions`, module, description, lifecycle/active state, audit fields, and optional introduced/deprecated release metadata). Specify authoritative schema and check it against P1/P6 schema preflight/manifest. Define a separate, auditable approval transition from unregistered/pending to `Active`; registry presence alone does not authorize a key.
- [ ] Create a new ordered DbUp migration; **backfill distinct keys from existing `RolePermissions` and `UserPermissions`** without removing/regranting existing assignments. Unknown legacy keys must be surfaced as **unregistered drift**, not accepted into the authoritative code registry. Backfill under a non-authorizing state; even a key that is later declared in code requires an explicitly reviewed adoption/activation decision before old grants can take effect. Preserve historical rows and report affected user/role grant counts without automatically approving them.
- [ ] Implement/enforce the runtime activation gate in Application authorization plus SQL permission snapshot (extend the existing `PermissionKeys.IsDeclared` / `PermissionAuthorizationService` and `SqlIdentityStore.GetSnapshotAsync` paths, or document an equivalent race-safe design). Evaluate catalog state and existing direct/role precedence consistently in one authorized snapshot; never treat a newly compiled constant as sufficient approval for preexisting SQL grants. If introducing foreign keys from assignment tables to `Permissions`, justify rollout/upgrade order and SQL compatibility first; never break existing installations or silently turn known historical permissions into grants. A no-FK staged design is acceptable if migration safety requires it.
- [ ] Design persistent metadata for the managed Administrator role, managed grant policy/revocation history and bootstrap completion marker, with unique constraints, immutable history where needed and documented ownership/permissions. These artifacts must be introduced through additive, ordered migrations; do not overload business `RolePermissions` rows with guesses about deleted grants.
- [ ] Update the **complete** controlled compatibility/privilege surface: `SchemaCompatibilityPolicy.CurrentScripts` (append post-`007` script(s)), `SqlSchemaCompatibilityChecker` object inventory/column and constraint fingerprints, `SqlRuntimePrincipalValidator`, `deployment/sql/Provision-MyDmsVnPrincipals.sql`, migration/package manifests and `docs/SCHEMA_COMPATIBILITY_AND_MIGRATION_RUNBOOK.md`. Add `SELECT` only on registry data genuinely needed at runtime; no runtime write to `Permissions`, managed grants, bootstrap state, `Users`, `Roles`, `UserRoles` or `RolePermissions` (retain the narrowly allowed password-column update on `Users`).

### P3.1-T03 — Repeatable sync engine: dry-run, apply and auditing

- [ ] Implement a privileged `permissions sync --dry-run` and `permissions sync --apply` (names illustrative; document final CLI). Produce a deterministic, reviewable plan: added definitions, changed descriptions/status, catalog activation/adoption decisions, new proposed Administrator grants, deprecated/unknown keys, and conflicts.
- [ ] Bind operator review to the **exact plan applied**. Emit a stable, non-secret plan ID/fingerprint of the deployed manifest/release, policy/approvals, target database identity and relevant expected DB state (catalog, managed-grant and assignments). `--apply` must require the approved plan ID/artifact and target, revalidate preconditions and recompute/compare state **inside** its serialized transaction. Manifest mismatch, policy change, approval expiry, changed grants or concurrent drift rejects apply with no mutation and requires a new dry-run/review. No `--force` bypass.
- [ ] **Additive/idempotent** reconciliation with bounded transaction, unique constraints and serialization/application lock: multiple runs and competing operators cannot create duplicate rows or partially grant permissions. Acquire the lock before re-reading expected state; verification and changes must share the same transaction/isolation boundary. On failure, roll back all planned changes. Audit unsuccessful attempts separately without falsely recording a committed change.
- [ ] Never automatically delete/revoke assignments or physically delete definitions when a key disappears. Mark an explicitly reviewed key deprecated and retain historical assignments; accidental registry omissions/rename are errors, not permission migration. Key rename requires reviewed mapping/ADR and safe migration.
- [ ] Never rewrite manually maintained role assignments or direct-user allow/deny rows. Persist managed-grant **ownership, operator approval and revocation/tombstone** keyed by the managed Administrator role identity plus exact key (e.g. additive `dbo.ManagedRolePermissionGrants` table). A missing `RolePermissions` row for a previously managed grant is drift/revocation, **not** an instruction to regrant; explicit/reviewed restore is the only path back. Detect direct/out-of-band SQL removals conservatively, retaining or creating a revoked record before routine sync continues. Existing manual grants never silently become managed grants; approval/policy changes are separately audited.
- [ ] Produce redacted, structured operator audit with release/manifest identifier, actor/principal, DB identity, UTC time, changes, outcome and reason; no password/hash/salt/connection string. Fail safely on unsupported DB, unexpected schema or incompatible registry.

### P3.1-T04 — Administrator role policy for new permissions

- [ ] Create `Administrator` role deterministically via normalized unique role name; distinguish **system-managed default role** from user-created roles with collision/ownership checks. Never impersonate an existing unrelated role.
- [ ] Initial enrollment may grant all **activated and approved** baseline permissions to Administrator. On later releases, propose eligible new keys and **previously pending keys explicitly approved in a later release**; re-running a release is idempotent. Never infer approval merely from a declaration, elapsed time or missing grant; other roles, direct overrides and manually owned grants remain untouched.
- [ ] Safe policy for sensitive keys (for example future security administration, destructive operations, export): **explicit release/operator approval** is required before Administrator auto-grant. Keep **catalog activation approval** separate from **Administrator grant approval**: an unactivated key is denied for everyone, while an activated key with an unapproved Administrator grant has no sync-created Administrator role assignment. Record independently reviewable statuses such as `Pending`/`Approved`/`Rejected` and `NotGranted`/`Granted`/`Revoked`, with actor/time/release; never treat a pending grant as an active grant. Review sensitivity by key, not just module names.
- [ ] If Administrator was manually denied via `UserPermissions`, that deny stays authoritative. If a managed Administrator role grant was explicitly revoked by an operator, routine sync must **not re-create it** without a separate approved restore action. Define a supported privileged revoke/restore workflow that updates the grant policy/tombstone and assignment atomically; for legacy or direct-SQL changes, missing managed assignment is treated as revoked and reported, not silently repaired.
- [ ] Document whether auto-grant is enabled by default for each permission definition, who approves policy changes and how to verify least-privilege impact across existing users.

### P3.1-T05 — Safe first-administrator enrollment CLI

- [ ] Add a deployment/DBA-only bootstrap command after schema migrations and registry sync. Accept database/target **through existing secure migration/admin configuration mechanism**; show sanitized target identity and require explicit confirmation/intent before mutation.
- [ ] Capture initial account details and a policy-compliant password from an **interactive masked/no-echo prompt** or an approved secret-input channel without process arguments or persisted plaintext; no password echo or sensitive exception payload. Reject noninteractive invocation requiring a prompt promptly (avoid CI hangs); support explicit `--non-interactive`/`--dry-run` for validation without creating a user.
- [ ] Use existing `IPasswordHasher`/BCrypt algorithm marker, password policy and username normalization. Preserve `PasswordSalt` compatibility sentinel; insert user, Administrator role/membership, required **approved** grants and a durable **bootstrap-completed marker** **atomically**, on the same locked transaction; require active account on success. The controlled sync-created, owned Administrator role and its approved grants may already exist before enrollment; bootstrap must not mistake that state for an existing user enrollment.
- [ ] **One-time guard** uses a persistent DB bootstrap-completion marker independent of user/account/role existence and activity, protected from runtime mutation; no counting `Users`/Administrator memberships as the sole proof. Under the lock, check both the marker and pre-existing identity data: completed marker always forbids enrollment even if the admin was later deleted/disabled; unexpected users/memberships/roles without a completion marker fail closed into recovery (apart from the verified system-owned Administrator role created by sync). Repeat invocation is a safe no-op/report, never a password reset, account takeover or role reassignment. Never silently elevate the first arbitrary user.
- [ ] Provide a separate, access-controlled lost-admin recovery procedure with operator authorization and audit (not ordinary bootstrap flags, not a bypass built into Login). Concurrency tests must prove only one enrollment wins and failure leaves no half-initialized administrator.

### P3.1-T06 — Deployment workflow and future-module integration

- [ ] Document deployment ordering: schema preflight/backup -> immutable DbUp migration -> validate registry manifest -> permission sync dry-run/review -> approved apply -> first-admin enrollment **only on new installation** -> post-check -> desktop login smoke. For upgrade: skip first-admin enrollment; sync known new definitions and grants under approved policy.
- [ ] Keep sync/provisioning **out of normal desktop startup, Login and background client processes**. Retain separate DBA/admin principal from restricted runtime SQL principal in `docs/CONFIGURATION_AND_SQL_SECURITY.md`; no auto elevation or installer-embedded credentials.
- [ ] Provide a **feature PR checklist**: add `PermissionDefinition`, register it, require permission in Application, update fixtures/snapshot, test new key denial/approved Administrator access, document sync/rollout. A new key that is used but not registered fails validation.
- [ ] Treat this schema upgrade as a **maintenance-window, stop-all-clients rollout** under the current P6 baseline: old clients built against `001`–`007` must return `Schema.TooNew` after the new migration, and new clients must return `Schema.TooOld`/incompatible against missing registry artifacts or unsynchronized registry. No rolling/mixed-version compatibility is supported until an explicit expand/contract ADR and tests prove it. Test both hosts' preflight, least-privilege SQL role, new release packaging and rollback limits; never imply that client downgrade reverses DB migration.

### P3.1-T07 — Verification and acceptance gates

- [ ] Fresh SQL database: migrate -> sync -> enroll first Administrator -> Login with provided credentials -> all **approved** baseline permissions succeed; inactive/unauthenticated accounts fail. No business Catalog seed required.
- [ ] Re-run provisioning/sync against populated DB: no duplicate role/user/key/membership/grant, no password reset, and no changed custom/direct permissions. Concurrent invocations serialize; injected failure rolls back.
- [ ] Release v2 adds `Sales.Orders.Read`, `Sales.Orders.Write` and a sensitive `Sales.Orders.Approve`: dry-run accurately reports additions; after reviewed activation/grant approval and apply, Administrator gets only eligible/approved grants; normal roles get no new grants; sensitive key stays denied if catalog activation is pending, and stays ungranted to Administrator if only its role grant approval is pending. Approve it in release v3 and verify a **late** approved managed grant is applied once without resurrecting revoked grants. Repeat is a no-op.
- [ ] Test a historical SQL `RolePermissions`/`UserPermissions` grant for a key absent from v1 code that later appears in v2 code: it **remains denied** until independently reviewed registry adoption/activation; an unknown, unregistered, pending or deprecated key cannot be activated by a preexisting SQL row or direct grant. Test direct deny overrides activated role grant and catalog state is checked consistently with permission assignment snapshot.
- [ ] Test manual grant remains manual, revoked managed Administrator grant retains durable tombstone (including out-of-band deletion), later routine sync never regrants it, and separate approved restore does. Verify new/late approvals, Administrator role ownership collision and permission drift.
- [ ] Test a preexisting P3 database with permission assignments, malformed manifests, mismatched schema, failed/competing syncs and unsupported/older clients. Verify dry-run/apply fingerprint match and stale-plan rejection after DB/approval/manifest changes, including concurrent change between review and apply; no partial write. Preserve historical assignments/data and log sanitized outcomes.
- [ ] Test bootstrap marker persistence across admin disable/deletion and application restart, concurrency racing two initial enrollments, preexisting users without marker, transaction failure before marker commit and the separately authorized recovery path. Verify neither a partially initialized identity nor a second Administrator is created.
- [ ] Integration tests use `MYDMSVN_TEST_SQLSERVER_CONNECTION_STRING` guarded disposable DB, not production; test command and actual pass/fail/blocked evidence required. Add CLI subprocess tests that assert no echo/no secrets/no modal prompts/no hangs.

## Acceptance / exit gate

- [ ] Document exact CLI syntax, preconditions, principal privilege split, dry-run/apply outputs, recoverability and administrator emergency recovery in a runbook.
- [ ] Permission registry and new SQL schema are additive and versioned, with proved non-authorizing backfill, **runtime activation enforcement**, deterministic plan-ID-bound sync, persisted Administrator grant approval/revocation policy and durable one-time bootstrap state.
- [ ] Fresh DB first admin can sign in through existing Application Login; no default password is present anywhere; repeated provisioning never changes that account.
- [ ] The **new feature permission lifecycle** (declaration -> registration -> catalog adoption/activation review -> migration/sync dry-run/approved apply -> managed-grant policy -> runtime authorization -> tests) is automated as far as safe and part of the development/release checklist; stale approval cannot apply and historical grants cannot bypass the gate.
- [ ] Evidence recorded; update `docs/SECURITY.md`, deployment docs/permission allowlists, `docs/DEVELOPMENT_PLAN.md` and this plan status only after verification.

## Avoid

Production seeding during desktop login; wildcard Administrator bypass; unconditional regrant of revoked privileges; destructive sync; guessing legacy hashes; SQL admin privileges in desktop packages; treating application Administrator as SQL `sysadmin`; marking SQL/Windows tests passed without execution.
