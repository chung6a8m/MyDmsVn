## Epoch rotation after replacement or rewind

[Schema012](../../src/MyDmsVn.Server.DbMigrator/Scripts/012_WebOperationJournal.sql) stores one `WebDeploymentState` row (`Id=1`, `DeploymentEpoch`, `RotatedAtUtc`). Ordinary worker restarts and multiple workers on one logical database retain that epoch. A database copy copies the epoch too. A clone into another logical deployment, restored/rewound history or replacement must receive a new epoch **before any browser or worker is readmitted**. Never rewrite historic journal epochs to make old intents match.

The current product exposes no rotation CLI/HTTP API. The following is the concrete procedure for a separately authorized operator using an audited SQL maintenance session; execution/rehearsal is NOT RUN for B06:

1. Identify the exact destination database and backup/recovery point privately, the approved operator, change ticket and correlation ID. Close admission for every worker and old tab; drain active transactions and confirm the maintenance target. Do not infer drain from a client abort or timeout. Preserve a recoverable backup and record its verified restoration plan before changing state.
2. Use the separate maintenance identity, never the Web runtime credential. Record an audit **attempt** with operator identity, old epoch, reason, target correlation and time in the protected durable audit sink. Audit access/retention is an operator prerequisite; no deployed B06 sink is supplied.
3. In one explicit transaction with bounded command/lock waits, require the expected old epoch and singleton row, generate a fresh nonempty GUID, and update only `DeploymentEpoch` and `RotatedAtUtc=SYSUTCDATETIME()` for `Id=1 AND DeploymentEpoch=@expectedOldEpoch`. Require exactly one affected row; otherwise roll back and investigate. Acquire the row through `UPDLOCK,HOLDLOCK` before checking/updating so concurrent maintenance is serialized. Commit before recording success. This describes SQL statements for an operator-owned session, not an installed command or permission to execute them now.
4. The [journal fence](../../src/MyDmsVn.Server.Infrastructure/Operations/SqlWebOperationJournal.cs) reads the same singleton with `HOLDLOCK` for the command/status transaction, then takes the exclusive transaction-owned key lock. Rotation must wait for those transactions; a timeout is not proof they stopped. If Commit acknowledgement is lost, stop, reconnect to the exact target and inspect the actual epoch before deciding the attempt's outcome. Do not blindly repeat rotation or claim success from the precommit audit.
5. Verify the persisted new epoch and audit the actual committed/indeterminate outcome. Confirm schema/principal admission and authenticated context on the matched artifacts. Under an explicitly authorized rehearsal, check stale-epoch write/status rejection, new context and lack of old-draft/layout restoration at the same origin/user ID. Fresh authentication must follow the existing account/session policy; epoch rotation alone is not session revocation. Do not expose copied production sessions/secrets in a clone.
6. Old local intents remain isolated under the old epoch. Old journal entries remain with their original epoch and actor/key tombstones; current readback cannot disclose them as a new-epoch result. Retain the reconciliation case and route users through frontend F05. If any check or audit is uncertain, keep admission closed.

Source test [WebOperationJournalTests](../../tests/MyDmsVn.Server.Infrastructure.Security.Tests/WebOperationJournalTests.cs) demonstrates rotation waiting for a held epoch transaction, stale-epoch rejection and compaction across stored/current epochs. That historical source/test evidence is not a deployed backup/restore drill or B06 execution result.

## Unknown-operation reconciliation

An operator case is evidence collection; there is no product administrative unlock endpoint. Keep the original intent locked and give the user a support correlation ID. Do not ask for JWT, refresh cookie, passwords, connection strings, complete raw drafts, HAR/trace or arbitrary result bytes. Keep authorized business evidence in restricted storage; publish only sanitized metadata and conclusions.

1. Record correlation ID, authenticated actor, current and original deployment epochs, operation ID, operation kind, canonical method/route, original request target (`null` for Create), expected fingerprint and observation time. The frontend rederives the fingerprint from its immutable original request using the pinned corpus. Never change key/payload/fingerprint to obtain a match; same numeric actor on a replacement database is insufficient.
2. Reauthenticate the original actor normally and verify active SQL session/account and the current operation-specific Write/Post grant. Prefer protected status through the existing client; do not impersonate another actor or add Read to recover a Write outcome. [Read repository](../../src/MyDmsVn.Server.Infrastructure/Operations/SqlWebOperationReadRepository.cs) and [controller](../../src/MyDmsVn.Server.HttpHost/OperationsController.cs) own current authorization and all identity checks. Auth failure, revocation, epoch mismatch or fingerprint conflict retains the lock and requires investigation.
3. When protected status is insufficient, a separately authorized operator inspects the exact actor/key row in the authoritative database with a narrowly scoped maintenance session. Record only identity, disposition, result document ID, timestamps, contract/codec versions and expiry first; do not dump `ResultBytes`. Match the stored epoch/kind/original target/fingerprint to the case before inspecting any authorized result. Use a consistent transaction/snapshot under the site's approved inspection procedure; do not combine unrelated live observations into proof.
4. Reconcile the identified document in `SalesReceipts`/`SalesReceiptLines` or `GoodsReceipts`/`GoodsReceiptLines`: status, stable line identities, quantities and version. For Post, correlate its `StockLedger` and `StockValuationEntries` with current `StockBalances`, source lines and intervening movements; check Q/V and frozen Sales COGS using exact decimal semantics. Current aggregate balances alone cannot identify an individual write. The [B05 physical oracle](WEB4_RECOVERY_PILOT_RUNBOOK.md) explains the tested independent source/ledger/value boundary; its disposable fixture/admin pipe is **not** production support tooling. Never insert/edit ledger or valuation rows to reconcile an HTTP acknowledgement.
5. Record observed facts, current authority, source/result availability, decision, operator/reviewer and retained case location. Give the user the sanitized correlation ID and current next step. Only the existing client path with a positively matched authorized original command outcome may settle its protected intent. A maintenance observation or later Get is not an importable status envelope and cannot manually unlock the session.

| Observation | Operator/user disposition |
|---|---|
| Valid matching `COMMITTED` original outcome | Client may settle through existing recovery after full identity checks. Create/Update return original Write detail/line IDs/version; Sales Post returns its original version; Receipt Post deliberately has no version. No extra Get/Read is needed for this command outcome. |
| `RESULT_EXPIRED`, `RESULT_UNAVAILABLE`, undecodable result or positive SQL completion without a usable original outcome | Preserve key/tombstone and record positive business evidence when justified. Current HTTP outcome is null or unusable, so do not fabricate a result or unlock the existing intent. Any later authorized fresh detail/version can support a separately permitted read/open flow, not replace the original response or resurrect an old editable snapshot. |
| Status404, absent row, timeout, cancelled browser request, lock wait failure or lost Commit acknowledgement | UNKNOWN. Absence is not rollback proof; a delayed original request can still arrive. Preserve the case and lock. |
| Epoch/fingerprint/actor/target mismatch or insufficient current grant | Do not disclose a result, rebind the intent or bypass authorization. Investigate the exact identity; remain fenced. |

[FenceAsync](../../src/MyDmsVn.Server.Infrastructure/Operations/SqlWebOperationJournal.cs) uses epoch `HOLDLOCK`, then `sp_getapplock` exclusive/transaction ownership on `MyDmsVn.WebOperation:<actor>:<operationId N format>` with a 10000ms lock timeout. Even taking and releasing that fence with no row does not exclude a later original request. Schema012 permits `CANCELLED`, but **no supported administrative terminal NOT_EXECUTED/CANCELLED protocol, CLI or client unlock is implemented or verified**. Never insert that tombstone manually, report CONFIRMED_NOT_EXECUTED, resend with a fresh key or manually duplicate Post. Same-key resend UI remains disabled pending real process-crash/Commit proof; B05's lost-response pilot does not open this gate.

## Retention, compaction and backups

The implemented result window is seven days after completion, at most 1MiB UTF-8 result bytes, encoded before the same business Commit. The stored command result is field-allowlisted; it contains sensitive business data, not credentials. SQL schema and [journal implementation](../../src/MyDmsVn.Server.Infrastructure/Operations/SqlWebOperationJournal.cs) enforce the window. Status treats an elapsed deadline as expired even before physical compaction. No automatic compaction scheduler is installed; the seven-day readback window does **not** guarantee physical deletion after seven days.

[SqlWebOperationMaintenance.CompactAsync](../../src/MyDmsVn.Server.Infrastructure/Operations/SqlWebOperationMaintenance.cs) is an explicit privileged API, absent from runtime DI, with no deployed operator CLI. A separately reviewed caller must own an explicit SQL transaction, database CONTROL authority, bounded execution, durable audit callback and commit/outcome handling. It supplies current epoch, stored row epoch, exact actor/key and correlation. The method validates authority, takes the current-epoch/per-key fence, audits the attempt with `ORIGINAL_LOGIN()`, then changes only eligible elapsed COMMITTED rows to EXPIRED and nulls result bytes. It returns affected rows; zero is not proof of a prior commit or rollback. Audit failure aborts before the update; the caller must roll back/dispose. A successful method return is still precommit: record successful compaction only after Commit, and treat lost acknowledgement as indeterminate until verified.

Keep permanent actor/key tombstones, original epoch/fingerprint/target/result identity and expiry. The immutable trigger permits only the eligible COMMITTED→EXPIRED transition and rejects delete/identity changes. Do not disable it, truncate/purge the journal, rewrite dates, reset keys or grant maintenance powers to the host. No bulk retention job or production compaction rehearsal is delivered here.

Backup the business tables, journal/tombstones and epoch as one consistent database recovery point. A backup can contain old sensitive result bytes even after live compaction, and restoring an older point can remove later tombstones or restore older sessions. Define protected backup access, at-rest protection/key custody, retention/deletion, restore testing, RPO/RTO and audit retention with named operators before production. Restore into isolation, close admission, validate the exact schema/principal/artifact set and rotate epoch for replacement/rewind using the procedure above before serving clients. Do not import a journal alone or use a backup to reconstruct and forge a client response. There is no accepted in-place12→11 downgrade; a separately planned whole-database/artifact recovery cannot silently carry old12 intents into a legacy deployment.
