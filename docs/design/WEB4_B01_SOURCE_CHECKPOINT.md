## 2. Selected same-UoW insertion design (B03/B04 implementation obligation)

`IUnitOfWork` exposes BeginTransaction, typed Repository, Commit/Rollback (`Persistence/IUnitOfWork.cs:7–17`). `SqlUnitOfWorkFactory.cs:39–43` opens one connection; the unit of work owns that connection, transaction and registered repository factories (`:46–113`). `ISqlExecutionContext` exposes this same connection/current transaction. Disposal rolls back a still-active transaction. `SqlPersistenceBuilder` is the registration seam; no alternate connection, ambient transaction, nested BeginTransaction or static context is allowed.

Use a narrow optional Application-owned operation context on the six commands, not on public Local DTOs: authenticated operation metadata plus a result codec interface. HTTP constructs the metadata only after wire validation/current server identity admission. Actor is taken from `ICurrentUserAccessor`, never from the client body/header. A Web-aware caller must supply complete context; a null context means the existing Local path, **not** a missing-header Web fallback. Local callers and desktop schema10 must never resolve/query the Web journal or epoch repository.

Planned paths (new names are design seams, not existing APIs): Application `Operations/WebOperationContext.cs`, `IWebOperationJournal.cs`, `IWebOperationResultCodec.cs`; Infrastructure `Operations/SqlWebOperationJournal.cs`; HttpHost `WebOperationWireCodec.cs` and `OperationsController.cs`. Resolve journal through `uow.Repository<IWebOperationJournal>()`, registered against `ISqlExecutionContext`. HTTP implements the Application-owned codec to project/validate/serialize the original DTO without I/O or authorization calls. Application depends on the interface, not HttpHost/Newtonsoft. The callback must finish before Commit and be bounded; serialization/size failure rolls back business+journal together.

For non-null Web context, each handler follows this order:

1. Keep existing pure shape/semantic validation and initial authenticated permission admission. Existing validators are deterministic; dynamic reference/current-status/stock checks are inside the transaction. Call the existing BeginTransaction exactly once.
2. Read the singleton current deployment epoch on this UoW connection with a shared lock held through transaction completion. Reject mismatch **before** key lookup, outcome disclosure or business work. Runtime has SELECT only. Privileged rotation requires exclusive access to this row and operator quiescence; it cannot overtake an admitted in-flight transaction. Never validate epoch on one database and mutate another.
3. Acquire an exclusive SQL transaction-owned operation-key application lock in the current database, resource derived from authoritative actorId + operationId (not user text), with finite timeout. A unique `(ActorUserId, OperationId)` constraint backs the lock. No committed PROCESSING reservation is needed. Lock ordering: epoch shared fence → operation key → existing posting coordinator → sorted stock/header locks; maintenance uses the same order. Lock timeout/deadlock is not automatically retried.
4. **After key wait**, recheck active session/account and required current grant on the same UoW connection/transaction. Initial OWIN and MediatR permission checks are not sufficient evidence after a wait. Existing `SqlWebAuthSessionStore`/identity stores open their own connections; B03 must add narrow transaction-bound reads, not call those independent methods as though they are part of this UoW. Keep active-key/direct-Deny/superuser-binding semantics identical to the existing permission service. Protect the checked authority rows through result selection/business commit so concurrent revocation cannot produce stale replay admission.
5. Read only this actor/key row. An existing different fingerprint/kind/epoch/target cannot execute; return the specified conflict without result leakage. A matching COMMITTED unexpired result returns exactly the stored original result; no dynamic business validation, reference reload, stock gate or Post execution. A matching expired/unavailable/cancelled tombstone never becomes a fresh command. Rows belonging to another actor are not searched or disclosed.
6. For an unseen key only, execute the original dynamic work beginning at the source seams in §1. Build the original result; strict codec/size check; insert the immutable identity plus COMPLETE result into the journal on this transaction; Commit once. Any precommit failure rolls back both. A failed Commit acknowledgement is uncertain; do not open a second transaction to mark success/failure or automatically execute again.
7. After Commit return the stored projection to HTTP and retain existing business audit placement. A client response loss is recovered by protected status, never by implicit replay. Explicit same-key resend remains gated on B03/B04 SQL concurrency/tombstone proof.

Status GET uses a short transaction with the same epoch fence and key ordering: recheck session/account, locate only the current actor/key identity row, resolve the required grant from its stored operation kind, then recheck that grant and compare the expected fingerprint before reading/disclosing the stored result. An absent/cross-actor row remains the same generic absence. It does not run a business handler, Get query or resolver using a different connection. An absent row remains non-affirmative even if no request was ever sent. Pure wire tests cannot establish lock semantics; B03/B04 must test two actual connections, delayed original versus explicit resend, revoke while waiting, rollback, commit-loss and worker restart.

## 3. Field-classified retention and bounded schema12 design

There is **no deployed Web operation retention/encryption policy or journal key configuration in the source pin**. `TraceSecurityAuditSink.cs:10` delegates audit destination/retention to the operator; that is unrelated to replay payload retention. B01 selects the following bounded nonproduction contract. It does not assert encryption-at-rest or production data-retention approval and invents no credentials/keys.

Persist only the exact original authorized success envelope field allowlist in the corpus: business IDs/date/version/ordered lines, original reference labels, money/quantity, original Post ack. These are confidential commercial data, not authorization evidence. Exclude raw requests, JWT/refresh/cookie/session secrets, passwords, addresses/phone/tax identifiers not present in that result, exceptions/traces, arbitrary DTO extension fields or current Get enrichment. Original field omission/null semantics remain module-specific. No general serializer may accept arbitrary objects.

The result codec has a hard **1,048,576-byte UTF-8** precommit limit. Source bounds: 200 Sales lines; note 1000 UTF-16 units (`SalesContracts.cs:9–10`), unit32 (`010_DirectSalesAndValuation.sql:196`), catalog code32/name256 (`003_Catalog.sql:5–7,36–37,63–64,96–97`) so combined labels are at most 291 units. A conservative fully escaped bound of 4096 bytes/line plus 32768 header is 851,968 bytes. Receipt original Write labels are null and the result is smaller. B03 must test maximum-shape serialization rather than truncate a result to fit; out-of-bound/unserializable outcome fails before business Commit.

For this bounded workstream, result expiry is **CompletedAtUtc + 7 days** (UTC). Runtime status checks expiry even before physical cleanup. An operator-owned, audited cleanup path can null expired result bytes under the same epoch/key lock; it cannot delete/reuse the key. Cleanup must be part of B03/B06 verification, with no promise that setting an expiry field erases bytes/backups by itself. Inability to decode/read a retained payload yields RESULT_UNAVAILABLE; expiry yields RESULT_EXPIRED. Both keep editable recovery locked. Immutable tombstones have **no automatic deletion or TTL**. Production encryption, backup destruction/retention and deployment-specific operator controls remain separate unapproved requirements.

Selected physical design for `012_WebOperationJournal.sql` (DDL and fingerprint to implement/verify in B03, not executed here):

| Object / field | Type / constraint / purpose |
|---|---|
| `dbo.WebDeploymentState` | Singleton key constrained to 1; non-null uniqueidentifier DeploymentEpoch and datetime2(7) RotatedAtUtc; operator inserts/rotates, runtime SELECT only. GUID is public identity, not a secret; rotate on clone/replace/history rewind, stable across workers/restarts. |
| `dbo.WebOperationJournal` identity | ActorUserId int positive + OperationId uniqueidentifier primary key; DeploymentEpoch uniqueidentifier non-null; contract/codec version; six-valued OperationKind; original RequestTargetId bigint null only for Create; RequestFingerprint binary(32). Method/canonical route derive from frozen version+kind; never from mutable client response metadata. |
| Result identity | ResultDocumentId bigint separately nullable; Create request target stays null even when result ID is assigned. Store the original result's target and checked kind relationship. |
| Disposition / payload | COMMITTED, EXPIRED or CANCELLED terminal disposition; bounded nullable varbinary(max) UTF-8 result bytes and codec version. RESULT_UNAVAILABLE is a read/decode failure, not permission to re-execute. CHECK length ≤1MiB; EXPIRED/CANCELLED have no response payload. |
| Timestamps | CreatedAtUtc, CompletedAtUtc, ResultExpiresAtUtc datetime2(7), UTC. COMMITTED has completion/expiry and result; EXPIRED keeps original completion/expiry; CANCELLED has administrative completion and no successful business result. |
| Immutability | PK, epoch, actor, operation kind, request target/hash, result document identity and original completion never change on replay/expiry. Cleanup can only compact payload/disposition. No committed in-progress row and no runtime DELETE. Constraints/triggers or narrowly owned statements must reject identity mutation in B03 tests. |

Safe negative operator disposition is **not an end-user API** in this contract: a privileged audited path must take the same key fence, recheck source/journal/in-flight evidence and commit CANCELLED/DO_NOT_EXECUTE tombstone before reporting confirmed-not-executed. A late original request then sees the tombstone and cannot run. If B03/B06 cannot implement/prove this protocol, the UI offers no negative unlock; positive result or gated exact-intent reconciliation remains the only path. A 404, expired result or deleting a local draft cannot create this proof.

## 4. Exact11 → 12 admission, grants and compatibility

Current `SqlWebSchemaCompatibilityChecker.cs:11` appends 011 to desktop CurrentScripts. Its exact11 definition check uses `SqlSchemaDefinitionFingerprint.Schema11 = 1B1CF2B760E4651A06D10F162E44418BB2A0DEF2E425EC9A901F55B71B03EC4F`. Desktop exact10 fingerprint remains `D8119C144DE35212FD495CF7F7BE7060A7FE6CAE55106ABD25AF795717BC0349` and scripts001–010 remain unchanged. The original 011 is not edited.

`DatabaseMigrationRunner.ValidateWebSchemaStateBeforeMigration:60–81` handles TooOld only by calling the desktop exact10 checker and `Schema10WebMaintenanceValidator`. Merely changing expected Web version to12 would classify exact11 TooOld, then fail desktop compatibility. B03 must add a standalone **frozen exact11** script-list + Schema11 artifact/fingerprint checker and `Schema11WebMaintenanceValidator`, independent of the new runtime Scripts list/count. Reuse the same migration-owned connection/exclusive migration lock and validated maintenance/drain/principal model; do not infer source validity from history row count.

| Source state / invocation | Selected admission |
|---|---|
| Empty, explicit `--web` | Existing fresh-install admission →001–012, then exact12 verification |
| Exact10, explicit `--web` | Existing exact10 maintenance gate retained →011 then012, then exact12 verification |
| Exact11, explicit `--web` | New frozen exact11 definition + maintenance gate →012, then exact12 verification |
| Exact12, explicit `--web` | Idempotent exact12 verification; no mutation beyond ordinary migrator behavior |
| Schema9/partial/spoofed11/unknown/too-new | Refuse; no inferred direct9→12 or loose history count admission |
| Desktop/Local | CurrentScripts stays exact10; absent operation metadata must use no Web tables; no mixed Desktop/schema12 writer rollout |

New exact12 definition fingerprint is generated from the implemented DDL under owned SQL tests in B03; B01 does **not** invent a hash for an uncreated schema. Schema11 source fingerprint constant and scripts001–011 must remain frozen. `SqlWebRuntimePrincipalValidator` and `Provision-MyDmsVnWebPrincipals.sql` enumerate allowed and forbidden object/column permissions, but do not currently verify all minimum required grants. B03 must add explicit undergrant checks as well as extend overgrant checks; adding only GRANT statements is insufficient.

Planned minimum Web principal delta: SELECT on WebDeploymentState; SELECT/INSERT on WebOperationJournal for key admission/result; tightly constrained UPDATE for payload compaction only if the selected implementation actually needs runtime cleanup (default: operator-owned cleanup, **no runtime UPDATE**). No runtime epoch INSERT/UPDATE/DELETE; no journal DELETE, schema ALTER/CONTROL, db_owner, unrestricted procedures or desktop grant widening. Immutable complete-row insert avoids an UPDATE requirement for ordinary writes. Separate migration/maintenance identity owns DDL, rotation and cleanup. Update both provisioning allowlist and under/overgrant validator, including inherited/column grants; test denied epoch mutation and journal identity changes.

Coordinated rollout: unchanged Web11 host/client remain on exact11 until Web12 backend and epoch-aware/keyed frontend are both ready; WEB4 host requires exact12, canonical headers and codec, no silent missing-key fallback. An old frontend must fail closed against WEB4 writes, not be granted unjournaled compatibility. Publish exact paired versions, clear/fence old runtime requests, ignore actor-only layout v1/v2, then allow authenticated epoch-scoped preview. F02 can consume this contract without pretending backend B04 endpoints already exist.
